# 故障排查

排查顺序应从控制器、数据库、SSH、BIRD 配置到 BGP 对端逐层进行。先收集只读证据，不要连续重复提交或直接删除数据卷。

## 快速状态检查

```bash
docker compose ps
docker compose logs --tail=200 birdbox
docker compose logs --tail=100 db
curl -i http://127.0.0.1:3000/api/health
```

健康接口正常示例：

```json
{"status":"ok","deploymentLocked":false}
```

`deploymentLocked:true` 表示有变更正在执行。等待其完成，不要重启容器。

## 页面打不开

检查端口发布：

```bash
docker compose ps birdbox
ss -ltnp | grep ':3000'
```

局域网访问需要 `.env`：

```dotenv
BIRDBOX_BIND_ADDRESS=0.0.0.0
```

修改后必须重建 Birdbox 容器。还要检查宿主机防火墙、云安全组和客户端到宿主机的路由。

## 登录后仍回到登录页

最常见原因是在 HTTP 环境设置了：

```dotenv
BIRDBOX_SECURE_COOKIE=true
```

纯 HTTP 测试应设为 `false`；生产 HTTPS 应保持 `true`，并让反向代理传递：

```nginx
proxy_set_header Host $http_host;
proxy_set_header X-Forwarded-Proto $scheme;
```

修改环境变量后重建容器，清除旧站点 Cookie 后重新登录。

## `/api/auth/sessions` 返回错误

- 未登录访问返回 `401 AUTH_REQUIRED` 是正常行为；
- 已登录却返回 `接口不存在`，通常是浏览器前端与旧 Node 后端版本不一致；
- 确认容器或进程已使用包含多会话功能的新版本重启；
- 检查 `/api/auth/status` 是否返回 `singleSession:false`。

```bash
curl -sS http://127.0.0.1:3000/api/auth/status
```

## 页面一直无法交互

变更期间置顶等待框会锁定交互，这是为了防止重复提交。先检查：

```bash
curl -sS http://127.0.0.1:3000/api/health
docker compose logs --tail=200 birdbox
```

- `deploymentLocked:true`：远端部署仍在进行；
- 网络请求仍 Pending：检查目标 SSH、BIRD Socket 和反向代理超时；
- 后端已经返回但页面仍锁定：记录浏览器控制台和 Network 面板后刷新页面；
- 反向代理 `proxy_read_timeout` 应大于最长远端变更时间。

刷新前先确认没有正在执行的部署。不要通过反复刷新和点击制造并发提交。

## 节点接入条件检查失败

先在目标节点重新执行页面生成的准备脚本，并保留完整标准输出和错误输出。然后检查：

```bash
test -f /etc/bird/bird.conf
test -S /run/bird/bird.ctl
stat -c '%U:%G %a %n' /run/bird/bird.ctl
id birdbox
birdc -s /run/bird/bird.ctl show status
```

常见原因：

- 页面填写的主配置、生成配置或 Socket 路径错误；
- BIRD Socket 不存在或属于 root 组；
- 专用用户未加入 Socket 用户组；
- 受管目录已存在但属主不符合预期；
- 生成配置路径已存在且不是安全的 `versions/` 符号链接；
- SSH 用户 Shell 为不可执行且脚本未成功修改；
- Include 未写入或完整主配置无法 reload；
- 容器到目标 SSH 地址不可达。

## 复制准备脚本提示无法访问剪贴板

Birdbox 会先使用浏览器 Clipboard API，失败后尝试浏览器的兼容复制方式。两种方式都可能被非安全 HTTP、浏览器权限策略、嵌入式页面或企业安全策略拒绝。

优先通过 HTTPS 打开 Birdbox，并允许站点使用剪贴板。如果仍失败，直接在脚本框中全选脚本文本并复制；不要只复制页面显示的一部分。执行前确认首行是 `#!/bin/sh`，末尾包含“Birdbox 节点准备完成”的成功提示逻辑。

## SSH 连接失败

从 Birdbox 容器使用托管身份执行只读 SSH：

```bash
docker compose exec birdbox ssh \
  -i /var/lib/birdbox/ssh/id_ed25519 \
  -o UserKnownHostsFile=/var/lib/birdbox/ssh/known_hosts \
  -o IdentitiesOnly=yes \
  -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  birdbox@router.example.net 'id; test -S /run/bird/bird.ctl'
```

非默认端口增加 `-p 2222`。不要在命令中打印私钥或真实认证信息。

## `known_hosts` 或 Host Key 错误

典型错误包括 `REMOTE HOST IDENTIFICATION HAS CHANGED`、`Host key verification failed`。

先在目标节点通过可信通道核对：

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

检查 Birdbox 记录：

```bash
docker compose exec birdbox \
  ssh-keygen -F 'router.example.net' -f /var/lib/birdbox/ssh/known_hosts
```

仅在确认是合法轮换后删除对应条目：

```bash
docker compose exec birdbox \
  ssh-keygen -R 'router.example.net' -f /var/lib/birdbox/ssh/known_hosts
```

然后在页面重新测试连接。非默认端口使用 `'[router.example.net]:2222'`。

不要删除整个 `known_hosts`。已有节点时 Birdbox 会把文件缺失、为空或缺少已知节点记录视为身份状态损坏并拒绝启动。

## 准备脚本提示主配置已存在内容冲突

Include 模式不会写入全局 Router ID，但 Birdbox 资源名称可能与主配置已有声明冲突。运行：

```bash
birdc -s /run/bird/bird.ctl configure check
```

查看 BIRD 报告的重复名称或语法位置。修改 Birdbox 资源的 BIRD 名称，或在经过评审后调整主配置声明。不要删除现有主配置内容来迁就自动生成配置。

## 候选配置检查失败

在页面查看“节点配置”中的候选内容和错误。常见问题：

- BIRD 名称重复；
- Function、Filter 或 Define 声明不完整；
- 资源引用了已停用或作用域不兼容的 Define；
- 自定义 Raw Block 有版本不支持的指令；
- 主配置中缺少自定义 Table、VRF 或基础声明；
- RPKI 文件路径不存在或 Include 语法错误；
- 当前节点 BIRD 版本与高级参数不兼容。

先修正单个资源并重新预检，不要绕过目标节点原生检查。

## Static 保存失败

| 错误 | 处理 |
| --- | --- |
| 没有可用完整 CIDR | Define 只有 `+`、`-`、`{}` 扩展前缀；加入精确 CIDR或使用自定义指令 |
| via 地址族错误 | IPv4 Static 使用 IPv4 Next Hop，IPv6 使用 IPv6 Next Hop |
| 冲突的静态路由动作 | 查找同节点同地址族其它 Static，让同一 CIDR 动作一致 |
| Define 不可用 | 启用 Define，修正地址族或作用域 |
| 资源不可移动 | 删除 Static 后在目标节点重新创建 |

修改 Define 后出现 Static 冲突，说明新增或改变的 CIDR 与其它 Static 的动作不同。统一动作后重新保存。

## 资源无法删除或改名

Birdbox 会保护引用关系。根据错误先处理：

- 会话中的 Function、Filter 或导出 CIDR Define；
- Static 选择的 CIDR Define；
- Function、Filter、表达式 Define 或 Static Raw 中的符号引用；
- RPKI 名称和 ROA Table 的源码引用。

按“会话/Filter -> Function -> 表达式 Define -> 基础 Define”的反向依赖顺序删除。

## 部署锁或数据冲突

`DEPLOYMENT_LOCKED` 表示另一个请求持有全局部署锁。`STATE_CONFLICT` 表示页面基于旧库存提交。

处理：

1. 等待当前操作结束。
2. 刷新页面。
3. 检查变更日志和实际节点配置。
4. 重新应用仍需要的变更。

不要重启 MySQL 来强制释放锁。数据库连接断开虽然会释放锁，但可能把远端部署留给恢复流程处理。

## Birdbox 启动失败

查看：

```bash
docker compose logs birdbox
docker compose logs db
```

常见原因：

- MySQL 密码、数据库名或用户不一致；
- 数据库结构比当前镜像更新或结构被人工修改；
- 控制器 SSH 私钥、公钥不匹配；
- 已有节点但 SSH 身份或 `known_hosts` 缺失；
- 未完成部署日志与库存不匹配；
- 数据卷属主不是容器用户 `10001:10001`；
- 端口或环境变量不合法。

保留现场，不要删除卷。优先从同一时间点备份恢复。

## BGP 配置已应用但未 Established

依次检查：

1. Peer IP、远端 ASN、本地 ASN 和端口；
2. 本地地址是否应留空，显式地址是否存在于节点；
3. Direct/Multihop、TTL、Interface 和 Link-local Scope；
4. TCP MD5/TCP-AO 是否双方一致；
5. 防火墙是否允许 TCP 179 或自定义端口；
6. Passive 是否导致双方都在等待；
7. BFD、Role、Require Capability 是否与对端兼容；
8. 目标 BIRD 日志和 `birdc show protocols all <protocol>`；
9. 对端日志中的 Notification 或能力协商失败。

示例：

```bash
birdc -s /run/bird/bird.ctl 'show protocols all birdbox_peer_example'
ss -tnp | grep ':179'
```

在 Birdbox 返回“配置已应用，正在等待远端 Peer”后，库存已经提交。修正参数时正常编辑并重新预检、应用，不要先强制删除节点。

## 收集问题信息

提交问题前收集并脱敏：

- Birdbox 镜像 tag 和 digest；
- `docker compose ps`；
- `/api/health` 结果；
- 相关时间段 Birdbox 和 MySQL 日志；
- 目标 BIRD 版本；
- 脱敏后的候选配置与 BIRD 错误；
- 操作步骤和受影响资源类型；
- 浏览器 Network/Console 错误。

删除 Peer IP、真实 ASN、认证密钥、Community、SSH Host Key 和私有路由策略后再公开分享。
