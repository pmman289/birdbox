# 生产最佳实践

本页给出 Birdbox 投入生产时的推荐基线。它不能替代组织自己的变更流程、路由安全政策和灾难恢复演练。

## 架构与访问

- Birdbox 运行在独立管理主机，不与生产 BIRD daemon 共用容器；
- Web 端口默认绑定 `127.0.0.1`，通过 HTTPS 反向代理访问；
- 必须监听局域网时，用主机防火墙只允许管理网段；
- SSH 出站只允许访问受管节点管理地址和端口；
- 数据库不向外发布端口；
- DNS、NTP 和备份目标都使用受控基础设施。

## 身份与会话

- 首次初始化前不要暴露到不可信网络；
- 管理密码使用密码管理器生成，至少 20 个随机字符；
- 管理员离职、设备遗失或怀疑泄露时立即修改密码，自动注销其它会话；
- 定期在“设置”中检查有效会话；
- 不共享浏览器 Cookie，不把多个操作员集中在同一个远程桌面会话中；
- Birdbox 当前只有固定 `admin` 账户，组织级责任归属应由堡垒机、反向代理日志或外部审计补充。

## 节点 SSH 安全

- 每个节点使用专用非 root 用户；
- 控制器公钥保持 `restrict` 选项；
- BIRD Socket 使用专用非 root 组；
- 不授予专用用户 sudo；
- 高安全环境在首次测试前通过可信通道核对 SSH Host Key；
- 合法轮换 Host Key 时只删除对应 `known_hosts` 条目，不清空整个文件；
- 定期检查 `authorized_keys`、受管目录属主和 Socket 组成员。

## 主配置边界

Birdbox 只拥有生成 Include 文件。系统管理员继续负责：

- 全局 Router ID；
- Kernel、Device、Direct 等基础 Protocol；
- 普通路由表和 VRF；
- BIRD 日志配置；
- Include 顺序和主配置中的其它声明；
- BIRD 软件升级。

不要在 Birdbox 生成文件中人工修改。不要让其它自动化工具同时写同一个生成配置路径。

## 资源作用域

- 只在多个节点语义完全一致时使用“所有节点”；
- 文件路径、VRF、Table 或 Cache 地址不同的资源使用节点级作用域；
- 全局资源修改会部署多个节点，应放入维护窗口；
- 使用稳定、可读的 BIRD 名称，不用临时工单号作为长期名称；
- 按 Define、Function、Filter、会话的依赖顺序创建，删除时反向执行。

## 路由策略基线

### Import

- 按客户、Peer、Transit 区分策略；
- 验证 Prefix、最大前缀长度、Bogon、AS_PATH、Origin ASN 和 Community；
- 对 RPKI 状态制定明确政策；
- 设置 Import 和 Receive Limit；
- Local Preference 由角色和合同决定，不在多个 Function 中重复覆盖。

### Export

- 默认“不导出”；
- 使用明确的 CIDR Define 作为允许列表；
- 检查自己的 Origin ASN 和合法 AS_PATH；
- 对客户、Peer、Transit 使用不同 Community 和 prepend；
- 设置 Export Limit；
- 只有路由表内容完全受控时才使用“导出所有”。

## 可视化策略与自定义 Filter

简单允许列表、Local Preference、prepend 和 Community 操作优先用可视化策略，便于审查。

复杂条件使用完整 Filter，并遵守：

- 所有分支有明确最终决定；
- 业务常量放入 Define；
- 重复逻辑放入 Function；
- 一条 Filter 只承担一个方向和一个角色；
- 保存前在测试节点或测试 Peer 验证。

## Static 路由

- Static 按用途分组，不按 BGP 会话复制；
- 同一 CIDR 在同一节点出现多次时保持动作一致；
- `via` Next Hop 纳入可达性监控；
- Blackhole/Reject 类路由使用独立 Define，并设置严格变更权限；
- 修改共享 CIDR Define 前检查所有 Static 引用；
- 自定义 Static 指令需要人工代码评审。

## RPKI

- 使用至少两个独立 Cache 或明确的故障降级策略；
- 先观察 `ROA_INVALID` 影响，再启用拒绝；
- 监控 RPKI Protocol 状态、Serial 更新和 ROA 数量；
- 本地 ROA 文件由独立可靠流程原子更新；
- 不把 Cache 密码、私钥路径和真实验证策略公开。

## 变更流程

推荐每次变更遵循：

1. 明确节点、Peer、Address Family 和资源影响范围。
2. 检查当前有效登录会话，确认没有他人同时编辑同一对象。
3. 记录变更前 BGP 状态和路由数量。
4. 先修改底层资源，再修改会话引用。
5. 手动点击“预检配置”，阅读生成配置。
6. 确认 Import/Export 默认拒绝位置和 Function 顺序。
7. 在维护窗口应用。
8. 等待置顶变更提示结束，不刷新或重启容器。
9. 检查 Established、路由数量、BIRD 日志和对端状态。
10. 记录结果；异常时停止继续变更并评估回滚。

## 并发操作

Birdbox 支持多登录会话，但远端部署全局串行。团队应使用变更频道或工单标识当前操作员和目标节点。

收到 `DEPLOYMENT_LOCKED` 或数据冲突时不要重复点击。刷新库存，确认前一个变更结果，再重新构造变更。

## 监控

至少监控：

- `/api/health` 可用性；
- Birdbox 和 MySQL 容器状态；
- 容器重启次数和日志错误；
- 数据卷剩余空间；
- 每个节点 SSH 可达性；
- BIRD daemon、控制 Socket 和配置加载结果；
- BGP Protocol 状态和路由数量；
- RPKI Protocol 和 ROA 数据新鲜度；
- 备份成功率和恢复演练结果。

健康接口只证明控制器进程和数据库可用，不证明任何 BGP 会话 Established。

## 备份和升级

- MySQL 与 `birdbox_data` 使用同一时间点备份；
- 备份文件按路由凭据等级保护；
- 至少每季度做一次隔离恢复演练；
- 升级前固定当前镜像 digest 并备份；
- 在测试环境验证目标版本；
- 不在远端部署执行期间升级或重启；
- 保留上一个已验证镜像用于回滚。

详细操作见 [[备份、升级与恢复]]。

## 敏感信息

以下内容不能提交到公开 Git、Issue 或聊天记录：

- `.env` 和数据库密码；
- `birdbox_data` 备份；
- 控制器 SSH 私钥和 `known_hosts`；
- TCP MD5、TCP-AO、RPKI 凭据；
- 未脱敏的 Peer IP、ASN、Community 和 Filter；
- 完整生产生成配置。

分享问题时使用文档前缀，例如 `192.0.2.0/24`、`2001:db8::/32` 和私有测试 ASN，并删除认证字段。
