# 备份、升级与恢复

Birdbox 的完整状态分布在 MySQL 和 `birdbox_data` 卷中。两者必须作为同一恢复点处理。

## 必须备份的内容

| 数据 | 位置 | 内容 |
| --- | --- | --- |
| MySQL | `birdbox_mysql` 卷 | 库存、管理员认证、登录会话、部署恢复日志 |
| 控制器数据 | `birdbox_data` 卷 | SSH 私钥、公钥、`known_hosts`、迁移文件 |
| 部署配置 | 仓库目录 | `docker-compose.yml`、`.env`、反向代理和防火墙配置 |

`.env`、数据库 dump 和数据卷归档都包含敏感信息，应加密保存并限制访问。

## 在线备份

先确认没有部署正在进行：

```bash
curl -fsS http://127.0.0.1:3000/api/health
```

返回 `deploymentLocked:false` 后，在仓库目录执行：

```bash
docker compose exec -T db sh -c \
  'MYSQL_PWD="$MYSQL_PASSWORD" exec mysqldump --single-transaction --no-tablespaces -u"$MYSQL_USER" "$MYSQL_DATABASE"' \
  > "birdbox-mysql-$(date -u +%Y%m%dT%H%M%SZ).sql"

docker compose exec -T birdbox tar czf - -C /var/lib/birdbox . \
  > "birdbox-data-$(date -u +%Y%m%dT%H%M%SZ).tar.gz"
```

两个文件名应记录同一个备份批次。另行备份 `.env`，不要把它放入公开仓库。

备份完成后至少验证：

```bash
test -s birdbox-mysql-*.sql
tar tzf birdbox-data-*.tar.gz | head
```

## 恢复原则

- 优先恢复到隔离主机验证；
- 使用同一时间点的 MySQL dump 和数据卷归档；
- 恢复期间停止 Birdbox，防止写入；
- 不要把生产数据恢复到仍可访问真实路由节点的测试环境；
- 测试恢复时通过防火墙阻断目标节点 SSH，或使用脱敏库存。

## 恢复控制器数据卷

停止 Birdbox：

```bash
docker compose stop birdbox
```

先备份当前现场。确认要覆盖后，使用目标归档恢复卷：

```bash
docker compose run --rm --no-deps --user 0:0 \
  --cap-add DAC_OVERRIDE \
  --cap-add CHOWN \
  --volume "$PWD/birdbox-data-YYYYMMDDTHHMMSSZ.tar.gz:/restore.tar.gz:ro" \
  --entrypoint sh birdbox -c '
    find /var/lib/birdbox -mindepth 1 -maxdepth 1 -exec rm -rf {} +
    tar xzf /restore.tar.gz -C /var/lib/birdbox
    chown -R 10001:10001 /var/lib/birdbox
  '
```

把文件名替换为实际备份。归档恢复后，控制器应继续使用原 SSH 身份和 `known_hosts`。

## 恢复 MySQL

Birdbox 保持停止状态，确保数据库容器运行：

```bash
docker compose up -d db
docker compose ps db
```

把 dump 导入应用数据库：

```bash
docker compose exec -T db sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql -uroot "$MYSQL_DATABASE"' \
  < birdbox-mysql-YYYYMMDDTHHMMSSZ.sql
```

在已有数据库上导入前必须保存现场。标准 `mysqldump` 包含表重建语句，但仍应先在隔离环境验证恢复流程。

启动并检查：

```bash
docker compose up -d birdbox
docker compose ps
docker compose logs --tail=100 birdbox
curl -fsS http://127.0.0.1:3000/api/health
```

登录后检查有效会话、节点、资源和生成配置。不要立刻执行批量变更，先确认控制器 SSH Host Key 和目标节点实际状态一致。

## 升级

升级前：

1. 确认 `deploymentLocked:false`。
2. 记录当前镜像 tag 和 digest。
3. 同时备份 MySQL 和 `birdbox_data`。
4. 阅读目标版本变更说明。
5. 在测试环境验证。

修改 `.env` 的 `BIRDBOX_IMAGE_TAG`，然后：

```bash
docker compose pull birdbox
docker compose up -d --no-deps birdbox
docker compose ps
curl -fsS http://127.0.0.1:3000/api/health
docker compose logs --tail=100 birdbox
```

`--no-deps` 避免无必要地重建 MySQL。数据卷会保留。

## 回滚

把 `BIRDBOX_IMAGE_TAG` 改回上一个已验证 tag 或 digest，执行相同命令：

```bash
docker compose pull birdbox
docker compose up -d --no-deps birdbox
```

如果新版本已经升级数据库结构，旧版本可能以“数据库由更新版本初始化”拒绝启动。这时不要强行改表，应恢复升级前的 MySQL 和 `birdbox_data` 同步备份。

## 部署中断恢复

远端配置切换前，Birdbox 会在 MySQL 写入部署恢复日志。进程或容器异常退出后，下次启动会在部署锁下尝试：

- 完成目标配置提交；或
- 回滚已应用节点。

启动期间不要同时人工改库存或远端生成文件。如果库存既不匹配旧状态也不匹配目标状态，Birdbox 会拒绝启动，避免覆盖未知修改。保留日志和现场，从同一备份点恢复。

## 从旧 JSON 安装迁移

旧安装可在首次连接全新 MySQL 前导入 `data/inventory.json`、`data/auth.json` 和 `data/ssh/`。Docker 镜像本身不包含这些文件。

在第一次启动前：

```bash
docker compose pull birdbox
docker compose run --rm --no-deps \
  --user 0:0 \
  --cap-add DAC_OVERRIDE \
  --cap-add CHOWN \
  --volume "$PWD/data:/migration:ro" \
  --entrypoint sh birdbox -c '
    cp /migration/inventory.json /var/lib/birdbox/inventory.json
    if [ -f /migration/auth.json ]; then
      cp /migration/auth.json /var/lib/birdbox/auth.json
    fi
    if [ -d /migration/ssh ]; then
      mkdir -p /var/lib/birdbox/ssh
      cp -R /migration/ssh/. /var/lib/birdbox/ssh/
    fi
    chown -R 10001:10001 /var/lib/birdbox
  '
docker compose up -d
```

已经初始化过的 MySQL 不会再次导入旧 JSON。迁移已有节点时必须同时保留原 SSH 身份和 `known_hosts`。

## 恢复演练清单

- 在隔离网络创建全新 Compose 环境；
- 恢复两个同批次备份；
- 验证管理员登录；
- 验证节点、Peer、会话和所有资源数量；
- 验证控制器 SSH 公钥指纹与生产备份一致；
- 在阻断真实节点访问的情况下打开页面；
- 记录恢复耗时和人工步骤；
- 修正文档后销毁演练环境和敏感数据。
