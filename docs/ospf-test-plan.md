# OSPF 管理功能测试分析与全量用例

本文用于 OSPF 管理功能的回归、发布验收和事故复盘。测试目标不是只确认配置字符串生成成功，而是验证从画布编辑、库存保存、远端下发到 BIRD 邻居收敛和路由传播的完整闭环。

> 文档状态：测试方案与用例基线。本文中的“通过条件”是必须由执行记录证明的验收标准，并不代表当前版本已经全部通过。实际执行时应在每个用例后填写结果、构建版本、环境、证据路径和缺陷编号。
>
> 覆盖规模：183 条编号用例，包含 24 条数据校验、19 条渲染、14 条 API、10 条事务、10 条并发、28 条 UI、20 条实机、10 条状态机、20 条高级选项、6 条生命周期、7 条安全、10 条运行态和 5 条性能用例。P0/P1 用例是发布阻断项。

### 阅读和执行方式

1. 先阅读“测试环境与安全准备”和“固定测试数据”，创建隔离节点、快照和证据目录；没有快照或无法清理的环境不得执行应用类用例。
2. 按 L0 → L1 → L2 → L3 的顺序执行。L0/L1 失败时先修复或记录缺陷，不得用较高层级的偶然成功覆盖低层级失败。
3. 用例表中的“操作与断言”是最小步骤。执行人还必须记录前置状态、实际输出、配置 diff、日志/截图、清理结果和缺陷编号。
4. 同一用例在不同 BIRD、Agent、浏览器或传输模式下重复时，沿用原用例 ID，并在结果中增加环境维度；只有新增行为才分配新 ID。

## 测试分析

### 测试目标与质量属性

本计划把 OSPF 管理视为一个跨控制器、Agent、BIRD 和浏览器的变更系统。测试目标包括：

- **功能正确性**：域、节点、链路、Area、协议版本、策略和高级选项能按用户输入保存并生成合法 BIRD 配置。
- **配置一致性**：预览、持久化库存、远端 Include/生成文件和 BIRD 活动配置代表同一版本；失败时不留下半套配置。
- **运行正确性**：OSPFv2/v3 邻居、LSA/路由、Cost 选路、撤销、重收敛和路径查询结果与 BIRD 实际输出一致。
- **隔离与恢复**：单节点、单域、单地址族或单请求失败不会扩大为控制器不可用；并发冲突可重试，应用失败可回滚。
- **兼容性**：旧库存、旧认证字段、旧布局、Agent/SSH 传输模式、OpenWrt BusyBox 和不同 BIRD 2.x 版本均有明确行为。
- **安全与可观测性**：输入不能注入 BIRD/ shell；凭据不泄露；关键变更、失败和回滚可追踪，轮询不刷屏。
- **可用性与性能**：预检和应用有明确等待状态，错误能定位到字段；大拓扑、长时间轮询和多会话不会锁死页面或耗尽队列。

### 测试策略与测试金字塔

L0 以纯函数和配置快照快速发现规范化、校验和渲染问题；L1 验证 HTTP、数据库 CAS、部署事务和权限；L2 用 Playwright 验证真实交互、响应式布局和错误恢复；L3 通过隔离节点的 BIRD 邻居和路由证明协议行为。高风险场景至少由两个层级交叉验证：例如策略顺序同时做渲染断言和 `bird -p` 解析，保存回滚同时做 fake executor 和实机故障注入。每个用例固定执行“准备快照 → 注入输入/故障 → 观察多层结果 → 清理并核对快照”四步，不能只验证单个 HTTP 状态或单个页面文本。

### 组合覆盖与取样规则

OSPF 的字段组合数量很大，不能只测一条“默认配置”或把每个字段单独通过视为完成。发布候选按下表做正交取样；表中每一行至少选择一个代表值，并将所有 P0 组合提升为强制实机或 `bird -p` 验证。

| 维度 | 代表值 | 最低覆盖要求 |
| --- | --- | --- |
| 地址族 | v2、v3、双栈 | 每种地址族至少覆盖单链路、三角形、策略和故障恢复；双栈必须证明 v2/v3 状态、路由和预览互不串值 |
| 传输方式 | Agent、SSH 兼容、OpenWrt BusyBox | 每种方式至少执行一次预检、应用、运行态查询、超时和恢复；OpenWrt 不得依赖 GNU 用户态命令 |
| BIRD 版本 | 2.17、2.19 及项目支持的最低版本 | 每个版本至少解析 v2、v3 和一组高级选项；版本不支持的字段必须在预检阶段给出明确错误 |
| 拓扑 | 空域、单链路、三角、全互联、平行链路、多 Area/Virtual Link | 空域必须无幽灵线段；平行链路必须区分接口且 cost 规则一致；多 Area 必须验证跨 Area 路由 |
| 策略 | all、none、Function、Filter、CIDR Define、组合链 | v2/v3、不同节点、不同作用域各至少一组；递归链和成环各至少一组 |
| 接口类型 | ptp、broadcast、nbma、ptmp、passive/stub | 默认输出 `type ptp`；共享接口只验证允许的类型和参数一致性；接口选择器不能跨端混用 |
| 认证/快速收敛 | none、simple、md5/cryptographic、BFD、TTL security | none 验证不输出认证；一致和不一致密钥各一组；故障检测和恢复记录实际收敛时间 |
| 变更结果 | 成功、字段错误、预检失败、部分应用失败、CAS 冲突、响应丢失、控制器重启 | 每种结果都要检查库存、远端文件、活动配置、journal、锁和 UI 遮罩；失败不得留下半套配置 |

组合执行采用“基础场景 + 单一变量 + 故障变量”的方式：先用默认三角形建立基线，再一次只改变地址族、策略、认证、Cost 或传输方式，最后在同一场景注入节点超时、BIRD 语法错误和 CAS 冲突。这样既能定位差异来源，又能覆盖高风险交互。对于无法穷举的组合，报告必须写明未覆盖的笛卡尔积、取样依据和残余风险。

### 结果判定与可观测性 Oracle

每个测试至少有一个“权威 Oracle”和一个“用户可见 Oracle”。权威 Oracle 以 BIRD 解析/运行态、库存 revision、远端文件 SHA256 和部署 journal 为准；用户可见 Oracle 以预览、错误字段、按钮状态、事件和详情弹窗为准。两者不一致时按 P0 处理，即使页面或 API 单独返回成功。

| 检查点 | 权威 Oracle | 用户可见 Oracle |
| --- | --- | --- |
| 配置语法 | 匹配版本的 `bird -p -c` 返回成功 | 预检成功，显示目标节点和地址族 |
| 活动协议 | `birdc show protocols all`、`show ospf state` | 节点会话状态、邻居数量和版本标签 |
| 路由传播 | `birdc show route protocol <name>`，对照下一跳和 Cost | 路由详情弹窗、路径查询方向和高亮 |
| 持久化 | inventory JSON、revision、配置 SHA256、journal | 保存成功提示，刷新/第二会话读取相同内容 |
| 失败隔离 | 失败节点回滚、其它节点配置不变、锁释放 | 节点级错误、其它节点仍可操作、遮罩可关闭 |
| 资源边界 | Direct/Kernel/BGP/Static 文件、协议列表和路由表 diff | OSPF 页面不显示或修改非 OSPF 资源 |

任何一侧没有证据时只能记为“未完成”。“邻居数量大于 0”不能证明地址族正确、接口正确或路由实际传播；“HTTP 200”不能证明事务已经提交。

### 测试范围

OSPF 功能由四条边界组成，测试必须跨边界验证，不能只测其中一层：

| 边界 | 被测内容 | 主要风险 |
| --- | --- | --- |
| 数据与领域层 | 域、节点、链路、Area、版本、策略、认证和高级参数的规范化、校验、迁移 | 非法数据落盘、旧数据被覆盖、两端配置漂移 |
| 配置生成层 | 每节点 OSPFv2/OSPFv3 配置、接口方向、策略顺序、Include 和 BIRD 语法 | 预览与下发不一致、协议冲突、错误路由泄漏 |
| 控制器与远端层 | API、部署锁、CAS、预检、逐节点应用、回滚、Agent/SSH 超时和运行态查询 | `STATE_CONFLICT` 风暴、半套配置、单节点故障拖垮控制器 |
| 用户界面与运行态 | 画布、链路编辑、策略编辑、遮罩、错误定位、缩放、详情弹窗和路径查询 | 页面锁死、误编辑、状态误导、移动端不可用 |

不在 OSPF 单元测试范围内的 BGP、Direct、Kernel 和源地址策略，仍需在 L1/L3 做交叉回归：OSPF 不得修改这些资源，也不得因为一个 OSPF 节点失败阻塞其它资源的操作。

### 风险分级

| 级别 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 可能造成生产路由中断、错误下发、配置分裂、数据丢失、控制器不可用或所有用户无法继续操作 | 阻断发布；必须有自动化回归和修复后复测 |
| P1 | 单域/单节点功能不可用、策略或状态显示错误、回滚不完整但影响范围可控 | 发布前必须通过；需要记录残余风险 |
| P2 | 非核心选项、兼容性或可观测性缺陷，不影响默认路径 | 进入版本门禁或明确延期 |
| P3 | 文案、间距、非关键视觉差异 | 可随版本迭代，不得掩盖 P0/P1 |

### 核心不变量

下列不变量适用于所有层级的用例，任何一项失败都要提升为至少 P1；涉及远端配置或库存一致性时为 P0：

1. 草稿、预览、持久化库存和远端活动配置的版本关系可追溯；预检不会写库存或切换活动配置。
2. 链路两端的节点、接口、Area、Cost 和版本关系明确；不能把一端的接口或策略渲染到另一端。
3. v2 与 v3 可以独立启用、独立查看和独立使用策略；同一节点的两套 channel 不能互相覆盖。
4. 任一节点失败只影响该节点及当前事务；控制器健康检查、其它节点和其它域仍可用。
5. 任何失败都不留下半份库存、半份 Include、孤儿协议、未清理恢复日志或未说明的远端状态。
6. 查询、轮询、布局保存等只读或 UI 状态操作不能创建部署任务，也不能无限增加队列长度。

### 用例书写和结果约定

每个执行记录至少包含：用例 ID、前置库存快照、构建版本、浏览器/Node/BIRD 版本、操作步骤、实际结果、HTTP 状态或 BIRD 输出、日志/截图路径、清理结果和缺陷编号。结果只能使用以下值：

- **通过**：所有断言和证据齐全。
- **失败**：至少一个断言不满足，必须关联缺陷并保留现场。
- **阻塞**：环境或依赖不可用，不能推断为通过；写明解除阻塞条件。
- **未执行**：本轮未安排，不能计入放行通过率。

禁止用“接口返回 200”“页面没有明显报错”或“邻居数量大于 0”替代配置、状态和一致性证据。

## 测试环境与安全准备

### 环境矩阵

| 环境 | 组件 | 必测组合 | 说明 |
| --- | --- | --- | --- |
| 单元 | Node.js 24、MemoryDatabase、原生 BIRD parser | 每次提交 | 不访问网络，不写生产文件 |
| API 集成 | Node.js 24、MySQL 8.4、隔离临时目录 | 每次发布候选 | 覆盖真实 CAS、事务和重启恢复 |
| 浏览器 | Chromium desktop、Pixel 7 viewport | 每次发布候选 | desktop/mobile 均监听 `pageerror` 和 console error |
| Linux 实机 | BIRD 2.17/2.19、Birdbox Agent | 发布候选 | 使用临时 socket、Include 和测试隧道 |
| OpenWrt 实机 | BIRD 2.x、BusyBox、Birdbox Agent | Agent 或脚本变更时 | 不假设 GNU `stat`、`bash`、`systemd` 存在 |

实机测试至少准备 3 台节点；需要 SSH 兼容时再加入第 4 台。节点可以使用测试 VM、network namespace 或专用 GRE，但必须保证测试前缀不会被现有生产协议宣告。

### 隔离、快照和清理

1. 测试开始前保存控制器库存、数据库 revision、部署恢复日志、每台机器的 `/etc/bird/bird.conf`、Birdbox Include/generated 文件、Agent 服务状态、BIRD socket、`ip addr`、`ip route`、`ip -6 route` 和 `ip rule`。
2. OSPF 测试只使用 `198.18.0.0/24`、`198.19.0.0/24`、`2001:db8:198:18::/64` 和 `2001:db8:198:19::/64`。禁止使用真实业务 ASN、真实路由前缀、密码或生产 Include 路径。
3. 所有测试协议名、域 ID、接口、临时文件和日志加 `bbtest_ospf_<run-id>` 前缀；测试配置必须通过单独的 socket 验证，不能直接 reload 生产 BIRD。
4. 任何“应用”用例都必须能在测试结束时按逆序删除域、撤销测试路由、删除临时 GRE/namespace、停止测试 Agent，并确认已有 BGP、WireGuard、GRE、OSPF、Direct、Kernel 配置的文本和 SHA256 与测试前一致。
5. 清理失败时用例只能标记为“失败”或“阻塞”，不能开始下一轮；先恢复快照并确认路由表无测试前缀。

### 入口和退出标准

进入发布候选测试前必须满足：代码构建成功、数据库迁移完成、测试账号和第二登录会话可用、BIRD 与 Agent 版本记录完成、节点基线无 OSPF 测试协议。退出发布候选测试必须满足：所有 P0/P1 通过、所有失败都有缺陷和风险接受人、所有实机清理完成、库存 revision 和远端配置一致、控制器重启后健康检查通过。

### 证据目录约定

每次测试使用独立目录 `artifacts/ospf/<YYYYMMDD>-<run-id>/`，至少保存：

- `inventory-before.json`、`inventory-after.json`、revision 和 `deployment_journal`；
- 每个节点的配置快照、配置 SHA256、`bird -p` 输出、`birdc show ospf state`、`show ospf neighbors`、`show route`；
- API 请求/响应（脱敏）、控制器日志、Agent 日志、浏览器 trace、失败页面截图；
- `result.md`，逐条列出用例状态、实际值、预期值、缺陷 ID、清理结果和操作者。

凭据、Cookie、私钥、TCP-MD5/TCP-AO 密钥和完整生产配置不得进入证据目录或测试报告；日志共享前先执行脱敏检查。

## 0. P0 问题分析与复现基线

### 0.1 `STATE_CONFLICT` 的风险模型

库存采用带 revision 的乐观并发控制。一次 OSPF 保存通常会经历“读取库存、规范化和校验、逐节点预检、逐节点应用、按旧 revision 提交”几个阶段。以下任一并发写入都可能使提交时 revision 过期：

- 另一个浏览器会话同时保存同一 OSPF 域或其它域。
- 拓扑拖动产生的布局 PATCH 与域配置 PUT 交错到达。
- 其它资源编辑、节点管理、Agent 注册/撤销等库存写入。
- 后台迁移、规范化或轮询逻辑错误地把只读请求变成写入。
- 远端应用耗时期间用户重复点击保存，或多个标签页同时提交。

这类冲突必须由服务端在部署事务边界内处理：重新读取最新库存、重新构造候选配置、重新预检并应用；已经下发过的节点必须先回滚。用户不能看到可恢复的 `STATE_CONFLICT`，也不能留下“远端是新配置、库存是旧配置”的分裂状态。达到重试上限时，应返回稳定且可理解的最终错误，同时控制器和其它节点仍可继续操作。

### 0.2 标准复现步骤

1. 准备至少 3 个隔离测试节点和一个包含两条链路的 OSPF 域，记录库存 JSON、revision、各节点活动配置和 `deployment_journal`。
2. 在客户端 A 打开域编辑页，修改 n1 的策略；在客户端 B 打开同一域，修改 n2 的 cost。两边同时点击“保存并应用”。
3. 在保存持续期间连续执行 `GET /api/dashboard`、`GET /api/ospf/:id/runtime`，并在第三个客户端拖动 n3 的位置。
4. 重复上述步骤 20 次，同时注入一次首节点预检失败、一次第二节点应用失败和一次数据库 CAS 冲突。
5. 收集 HTTP 状态和响应体、事件日志、部署日志、库存 revision、远端 `birdc show protocols` 和生成配置 SHA256。

### 0.3 通过判定

- 并发保存最终按服务端定义的顺序成功，或只有最后一次返回明确的业务冲突；不得大量返回 `STATE_CONFLICT`。
- 每次失败均保持库存、活动配置、资源文件和恢复日志的一致性；不得出现半套 OSPF 配置。
- 预检和运行态 GET 不推进库存 revision；布局保存只改布局，不触发 BIRD 应用。
- 单节点失败只影响该节点和本次事务，控制器健康检查、其它节点操作和下一次保存均可用。
- 重试、回滚和最终失败各产生一条关键事件，禁止对每次轮询刷屏。

## 1. 测试分层与放行标准

| 层级 | 运行方式 | 覆盖目标 | 发布要求 |
| --- | --- | --- | --- |
| L0 单元 | `npm test` | 规范化、校验、渲染、解析、并发状态 | 全部通过，禁止跳过新增 P0 用例 |
| L1 API | Node test + MemoryDatabase/MySQL | HTTP 契约、CAS、部署回滚、节点隔离 | 所有 P0/P1 通过 |
| L2 UI | Playwright 桌面 + Pixel 7 | 表单、画布、弹窗、加载和错误状态 | 无 page error、无水平溢出、关键断言通过 |
| L3 实机 | 控制器 + 3 台 Linux/OpenWrt Agent | BIRD 邻居、路由、重启和故障恢复 | 三角形、全互联、双栈场景均收敛 |

P0 规则：任何数据丢失、错误下发、配置预览与实际配置不一致、页面锁死、并发保存返回 `STATE_CONFLICT`、单节点失败导致整个控制器不可用，均视为阻断发布。

## 2. 固定测试数据

### 2.1 节点

使用不包含生产数据的 `n1`、`n2`、`n3`、`n4`，每个节点至少返回以下接口：

| 节点 | Router ID | OSPFv2 接口 | OSPFv3 接口 | 备注 |
| --- | --- | --- | --- | --- |
| n1 | `192.0.2.1` | `ptp12`、`ptp14` | `ptp12`、`ptp14` | Agent |
| n2 | `192.0.2.2` | `ptp21`、`ptp23`、`ptp24` | 同名 | Agent |
| n3 | `192.0.2.3` | `ptp32`、`ptp34` | 同名 | Agent |
| n4 | `192.0.2.4` | `ptp41`、`ptp42`、`ptp43` | 同名 | SSH 兼容节点 |

预置两个策略资源和两个 Define：

- `fn_accept_n1` 只作用于 `n1`，`fn_reject_n2` 只作用于 `n2`。
- `filter_n1` 只作用于 `n1`，`filter_global` 作用于全部节点。
- `OSPF_V4_EXPORT` 类型 `cidr4`，`OSPF_V6_EXPORT` 类型 `cidr6`。

### 2.2 拓扑

测试数据按以下阶段复用：

1. 单链路：`n1 - n2`。
2. 三角形：`n1 - n2 - n3 - n1`。
3. 全互联：`n1`、`n2`、`n3`、`n4` 两两连接。
4. 平行链路：`n1` 与 `n2` 使用两条不同接口的链路；再测试 NBMA/PtMP 共享接口。
5. 多 Area：Area `0.0.0.0` 与 `0.0.0.1`，另加一条跨非骨干 Area 的 Virtual Link。

### 2.3 地址、路由和收敛阈值

测试地址必须与生产地址、主控管理地址和真实业务路由隔离。建议固定如下夹具，若环境地址不同只能整体替换，不能混用生产前缀：

| 用途 | IPv4 | IPv6 | 说明 |
| --- | --- | --- | --- |
| Router ID | `192.0.2.1` 至 `192.0.2.4` | 不适用 | 每节点唯一，OSPFv2/v3 可共用 Router ID |
| n1 测试路由 | `198.18.1.1/32` | `2001:db8:198:18::1/128` | 仅 n1 注入 |
| n2 测试路由 | `198.18.2.2/32` | `2001:db8:198:18::2/128` | 仅 n2 注入 |
| n3 测试路由 | `198.18.3.3/32` | `2001:db8:198:18::3/128` | 仅 n3 注入 |
| n4 测试路由 | `198.18.4.4/32` | `2001:db8:198:18::4/128` | 仅 n4 注入 |
| 备用汇总 | `198.19.0.0/24` | `2001:db8:198:19::/64` | Area、Filter 和截断测试 |

默认使用点到点接口和 `type ptp`，Hello 取 1 秒、Dead 取 5 秒；测试报告记录实际值。邻居达到 `Full/PtP` 的最长允许时间为 60 秒，链路/路由撤销在 3 个 Dead 周期（或实现定义的收敛上限）内完成。超过阈值必须记录 BIRD、Agent、内核和隧道状态，不能直接判定为“网络慢”。

### 2.4 夹具生成规则

L0/L1 使用内存对象或 JSON fixture，不访问测试机；L2 通过 Playwright `route.fulfill` 注入同一份库存和运行态；L3 使用独立 BIRD socket、临时 Include 和专用 GRE/network namespace。三层应共享节点 ID、协议名和测试前缀，以便对照配置和运行态证据。所有夹具在用例结束后删除，不能写入仓库中的生产配置样例。

## 3. L0 数据模型与校验用例

每个用例都要断言：请求失败不改变原库存；错误信息指出字段；不会生成或下发部分配置。

| ID | 场景 | 操作与断言 | 级别 |
| --- | --- | --- | --- |
| OSPF-VAL-001 | 空域 | 无节点、无链路可以保存；画布无线段、运行详情显示空状态 | P0 |
| OSPF-VAL-002 | 节点配置去重 | 相同 `nodeId` 两条配置必须拒绝 | P0 |
| OSPF-VAL-003 | 链路节点引用 | 不存在节点、同节点自环必须拒绝 | P0 |
| OSPF-VAL-004 | 接口完整性 | 本端或对端接口为空必须拒绝；两端接口名称按端点独立保存 | P0 |
| OSPF-VAL-005 | 端点自动启用 | 链路存在时两端 `enabled` 为 false，规范化后都为 true；删除最后一条链路不应误启用其它节点 | P0 |
| OSPF-VAL-006 | 版本选择 | v2、v3 可单独或同时启用；至少保留一个版本；禁用 v2 不得影响 v3 策略 | P0 |
| OSPF-VAL-007 | 策略隔离 | n1/n2 使用不同 import/export action、Function、Filter、Define；切换节点、保存、重新加载后值仍分别保持 | P0 |
| OSPF-VAL-008 | 版本策略隔离 | 同一节点 v2 与 v3 使用不同策略；生成配置分别落在 IPv4/IPv6 channel | P0 |
| OSPF-VAL-009 | 作用域 | 节点本地 Function/Filter/Define 被其它节点引用必须拒绝；全局资源可被所有节点引用 | P0 |
| OSPF-VAL-010 | Cost 统一 | 同一节点对多条平行链路 cost 不一致必须拒绝；一致时允许保存 | P0 |
| OSPF-VAL-011 | 接口复用 | PTP/Broadcast 复用同一端口必须拒绝；NBMA/PtMP 仅在 Area、hello/dead、认证等参数一致时允许 | P1 |
| OSPF-VAL-012 | 数值边界 | cost 1/65535、hello 1/65535、dead=hello、dead<hello、instance 0/255、tick、ECMP、优先级、TTL、DSCP 等边界分别测试 | P1 |
| OSPF-VAL-013 | Area 约束 | Area 必须 IPv4；Backbone 禁止 Stub/NSSA；Networks/External/Stubnet 前缀、tag、cost 非法时拒绝 | P1 |
| OSPF-VAL-014 | Virtual Link | Router ID 和传输 Area 必须为非 Backbone IPv4；时间、认证、密码参数完整校验 | P1 |
| OSPF-VAL-015 | 认证组合 | none 不输出认证指令；simple/md5/ipsec 生成正确；OSPFv3 simple 必须拒绝；密码选项完整保留 | P1 |
| OSPF-VAL-016 | 旧数据兼容 | 缺失 `options.type`、旧认证字段、旧 layout、旧 node config 读取后补默认值且不丢字段 | P0 |
| OSPF-VAL-017 | 布局清理 | layout 中不存在的节点被移除；合法节点坐标四舍五入并保留 locked | P1 |
| OSPF-VAL-018 | 依赖递归与成环 | Function、Filter、Define 互相引用形成直接或间接环时拒绝保存；无环链按依赖顺序通过 | P0 |
| OSPF-VAL-019 | 资源删除保护 | 删除或停用被 OSPF 引用的资源时拒绝操作，错误指出域、节点、地址族和资源；未引用资源可删除 | P0 |
| OSPF-VAL-020 | 协议/Include 冲突 | 域 ID、协议名、Include 路径与现有 OSPF/BGP/Direct/Kernel 冲突时拒绝或按兼容规则复用，不能覆盖用户配置 | P0 |
| OSPF-VAL-021 | 重复提交幂等 | 相同请求 ID 或相同草稿重复提交只产生一个版本、一个部署事务和一组协议 | P0 |
| OSPF-VAL-022 | 节点地址与传输兼容 | 节点公网 SSH 地址、端口、IGP 地址和 Agent endpoint 分离保存；修改连接地址不改变 OSPF 接口配置 | P1 |
| OSPF-VAL-023 | 地址族策略独立 | v2/v3 的 import、export、Define、Function 和 Filter 可分别设置；缺少某一地址族字段时使用兼容默认值 | P0 |
| OSPF-VAL-024 | 自动资源边界 | 创建或更新 OSPF 域不得自动创建 Direct/Kernel/Static 等资源；只兼容读取显式存在的资源 | P0 |

## 4. L0 配置渲染与 BIRD 语法用例

对每个组合执行 `bird -p -c <generated.conf>`；除断言字符串外，必须以 BIRD 实际解析成功为准。

| ID | 场景 | 关键断言 | 级别 |
| --- | --- | --- | --- |
| OSPF-REN-001 | v2/v3 双栈 | 协议名称稳定、唯一、长度不超过限制；分别生成 v2 和 v3 | P0 |
| OSPF-REN-002 | 禁用节点 | 节点 `enabled=false` 时不渲染 OSPF 协议；其它节点配置不受影响 | P0 |
| OSPF-REN-003 | 自动 Router ID | Router ID 留空时由 BIRD 自动选择；填写时只影响当前节点 | P1 |
| OSPF-REN-004 | 默认 PTP | 未提供 type 时明确输出 `type ptp;`；不默认输出认证 | P0 |
| OSPF-REN-005 | 端点方向 | 从节点 A 渲染使用 `localInterface`，从节点 B 渲染使用 `remoteInterface`；不能把对端接口写到本端 | P0 |
| OSPF-REN-006 | 平行链路 | 不同物理接口生成独立 interface block；NBMA/PtMP 共享接口合并 neighbors | P1 |
| OSPF-REN-007 | 基础策略 | import/export all、none、cidr、combined、custom Filter 分别生成正确语法 | P0 |
| OSPF-REN-008 | 策略顺序 | Function 按步骤顺序执行；静态重分发的 `if source = RTS_STATIC then accept;` 位于终止动作前 | P0 |
| OSPF-REN-009 | 高级协议 | rfc1583compat、rfc5838、instance id、stub router、tick、ECMP、merge external、graceful restart 全部按开关输出 | P1 |
| OSPF-REN-010 | Area 属性 | stub、nssa、summary、default cost、translator、networks、external、stubnet 全部输出且无重复 area | P1 |
| OSPF-REN-011 | Interface 属性 | poll、retransmit、transmit delay、priority、wait、dead mode、rx/tx、bfd、ttl、DSCP、密码、neighbors 全部输出 | P1 |
| OSPF-REN-012 | Virtual Link | 虚链路及其认证、时间和密码选项生成可解析配置 | P1 |
| OSPF-REN-013 | 互不污染 | n1 的配置预览只包含 n1 的 OSPF 段；切换 n2 后预览立即变化，不显示 n1 的策略或接口 | P0 |
| OSPF-REN-014 | 复杂组合 | v2-only、v3-only、双栈、无链路、有 Area 无链路、多个域同时存在均可解析 | P0 |
| OSPF-REN-015 | 现有配置兼容 | 节点已有主配置、Include、BGP、Direct 或 Kernel 时，只追加受管 OSPF 段；禁用/删除域后只移除自身内容 | P0 |
| OSPF-REN-016 | 依赖展开顺序 | Function/Filter/Define 按拓扑排序输出，重复定义只输出一次；检测到环时不生成候选配置 | P0 |
| OSPF-REN-017 | 版本/域隔离 | 同一节点多个域及 v2/v3 协议名稳定唯一，禁用一个域或地址族不影响其它协议 | P0 |
| OSPF-REN-018 | 预览实时性 | 节点、链路、策略和高级字段每次有效修改都立即反映到预览；旧异步响应不能覆盖最新草稿 | P0 |
| OSPF-REN-019 | 无孤儿资源 | 删除/禁用 OSPF 域只移除自身协议和 Include；不生成、删除或改写 Direct/Kernel/Static/BGP 资源 | P0 |

## 5. L1 API 与部署事务用例

### 5.1 HTTP 契约

| ID | 请求 | 预期 |
| --- | --- | --- |
| OSPF-API-001 | `GET /api/ospf`，空库存 | 200，domains/layout/inventory 结构完整 |
| OSPF-API-002 | `POST /api/ospf` | 只创建一个域，返回 domain、inventory、deployment、events |
| OSPF-API-003 | `PUT /api/ospf/:id` | 只更新目标域；其它 OSPF 域、BGP、资源不变 |
| OSPF-API-004 | `POST /api/ospf/preview` | 只预检不持久化、不切换远端活动配置；返回每节点 config 和 validation |
| OSPF-API-005 | `PATCH /api/ospf/layout` | 只改全局布局，不触发远端 BIRD 应用；过滤未知节点 |
| OSPF-API-006 | `PATCH /api/ospf/:id/layout` | 只改目标域布局，增量合并，不删除其它节点坐标 |
| OSPF-API-007 | `GET /api/ospf/:id/runtime` | 按域节点返回 v2/v3 状态、邻居详情、路由详情；单节点失败仍返回其它节点 |
| OSPF-API-008 | 非法 JSON/ID/域不存在 | 400/404，错误可读，库存 revision 不变 |
| OSPF-API-009 | 重复/幂等请求 | 使用相同请求 ID 重复 POST/PUT/DELETE；只产生一个最终版本，重复请求返回可识别的幂等结果 |
| OSPF-API-010 | 权限和会话 | 未登录、过期会话、只读用户和管理员分别调用所有 OSPF 端点；权限错误不改变库存，成功操作可被第二会话读取 |
| OSPF-API-011 | 路由路径查询 | 使用 IPv4、IPv6、无路由、ECMP 和环路目标；返回起点、下一跳、经过节点、方向和可读失败原因 |
| OSPF-API-012 | 部分运行态响应 | 多节点并行查询时让一个节点超时或返回坏数据；HTTP 在有界时间内返回，其余节点结果完整并带节点级错误 |
| OSPF-API-013 | `DELETE /api/ospf/:domainId` 删除已存在域、重复删除不存在域 | 首次删除只移除目标域及其受管 OSPF 片段；其它域、BGP、Direct、Kernel、Static、布局和用户 Include 不变；重复删除返回稳定 404 |
| OSPF-API-014 | `GET /api/nodes/:nodeId/interfaces` 在 Agent、SSH、空接口和节点超时场景下调用 | 返回去重后的合法接口名；失败只返回目标节点错误，不阻塞其它节点和 OSPF 编辑；接口名不能注入配置 |

### 5.2 事务、并发与故障注入

| ID | 故障注入 | 预期 |
| --- | --- | --- |
| OSPF-TXN-001 | 4 个客户端同时 PUT 同一域 | 不向用户暴露可恢复的 `STATE_CONFLICT`；服务按最新库存重试，最终成功或返回明确的最终失败 |
| OSPF-TXN-002 | 远端应用耗时期间并发 GET dashboard/runtime/interfaces | GET 不写库存、不推进 revision；部署最终 CAS 成功 |
| OSPF-TXN-003 | 拖动布局与域保存同时发生 | 布局增量合并，域配置不丢；不得出现 revision 冲突 |
| OSPF-TXN-004 | 第一个节点预检失败 | 不应用任何节点，不改变库存，返回失败节点和 BIRD stderr |
| OSPF-TXN-005 | 第二个节点应用失败 | 已应用节点全部回滚；库存保持旧版本；恢复日志清理成功 |
| OSPF-TXN-006 | 库存提交第一次 CAS 冲突 | 远端回滚后重新读取、重新预检、重新应用；最多 3 次，测试日志为 warning 而非 error 风暴 |
| OSPF-TXN-007 | 连续 3 次 CAS 冲突 | 返回可识别错误，恢复日志可恢复，控制器仍可 GET/操作其它节点 |
| OSPF-TXN-008 | Agent 超时/断线 | 当前节点状态明确为失败或未知，不阻塞其它节点和后续健康检查 |
| OSPF-TXN-009 | 重复点击保存/预检 | 同一页面只允许一个动作；不会生成重复部署或重复域 |
| OSPF-TXN-010 | 多个 OSPF 域 | 更新域 A 不触碰域 B 的配置、协议名、邻居和节点策略 |

### 5.3 多配置保存专项回归（P0）

以下用例必须在每次发布前执行，不能用“接口返回 200”替代一致性检查。每个用例至少重复 20 轮，并同时覆盖 MemoryDatabase 和 MySQL。

| ID | 并发参与者 | 注入时机 | 详细步骤 | 通过条件与证据 |
| --- | --- | --- | --- | --- |
| OSPF-CONC-001 | A、B 同一域不同节点参数 | 两次 PUT 同时发出 | A 修改 n1 策略，B 修改 n2 cost，同时保存 | 至少一次成功；若重试，响应不含 `STATE_CONFLICT`；最终域同时保留双方修改或按明确的最后写入规则落盘；抓取两次响应、最终库存和 revision |
| OSPF-CONC-002 | A、B 两个不同 OSPF 域 | 远端预检进行中 | 同时保存域 A、域 B | 两域均可完成或一方得到“部署进行中”提示；不得互相覆盖、重复协议或留下活动 journal；记录域 ID、节点配置 SHA256 |
| OSPF-CONC-003 | 保存 PUT、布局 PATCH | PUT 应用前 | A 保存域配置，B 连续拖动 3 个节点并 PATCH | 配置和布局都保留；布局 PATCH 不触发远端应用；revision 单调递增且无冲突风暴 |
| OSPF-CONC-004 | 保存 PUT、资源编辑 PUT | 节点逐个应用之间 | A 保存 OSPF，B 修改被 OSPF 策略引用的 Function/Filter | 服务重新读取并校验依赖；最终配置中引用版本唯一；失败时所有已应用节点回滚 |
| OSPF-CONC-005 | 三个保存客户端 | 第一次 CAS 提交前 | A/B/C 连续修改同一域并发提交，模拟三次 revision 变化 | 服务按上限重试；最终失败必须是可读业务错误且控制器仍能 `GET /api/health`、读取域和保存其它域 |
| OSPF-CONC-006 | 保存 PUT、后台轮询 | 远端应用持续 5 秒 | 保存期间每 100ms 请求 dashboard、runtime、interfaces | 轮询完全只读，不推进 revision，不产生部署任务；保存一次完成，事件日志无重复“检查通过” |
| OSPF-CONC-007 | 应用成功、提交响应丢失 | CAS 已提交后断开连接 | 让数据库写入成功但 HTTP 响应超时，再重试同一请求 | 服务确认 durable state，不重复回滚已成功配置；重试为幂等操作，库存和远端配置只有一个版本 |
| OSPF-CONC-008 | 第二节点应用失败 | 第一节点已成功应用 | 注入第二节点 `bird -p` 或 `configure` 失败 | 第一节点恢复旧配置，第二节点无半成品；库存 revision 不变，journal 清理或可恢复，下一次保存可成功 |
| OSPF-CONC-009 | 预检失败与并发保存 | 预检阶段 | A 提交非法接口，B 同时提交合法修改 | A 不写库存、不应用任何节点；B 不被锁死且可成功；错误字段和节点明确 |
| OSPF-CONC-010 | 重启恢复 | journal 标记 rollback/forward 后重启控制器 | 在保存中止进程，重启后观察恢复，再发起新保存 | 恢复只执行一次；journal 清空；新保存不返回 `STATE_CONFLICT`，节点活动配置与库存一致 |

每轮测试结束后执行以下一致性检查：

```sh
# 控制器
curl -fsS http://127.0.0.1:3000/api/health
curl -fsS http://127.0.0.1:3000/api/ospf

# 每个隔离节点（按实际 socket 替换）
birdc -s /run/bird/bird.ctl show protocols all
birdc -s /run/bird/bird.ctl show ospf state
sha256sum /etc/birdbox/generated.conf /etc/birdbox/resources/*.conf
```

应保存响应体、HTTP 状态、`deployment_journal`、库存 revision、事件日志和节点命令 stderr；缺少任一证据时用例只能标记为“未完成”，不能标记通过。

## 8. 性能、安全与持久化

- 20 节点、100 条链路、v2/v3 双栈下，预览响应、画布渲染和运行详情不得阻塞浏览器；页面长任务必须有等待状态。
- 运行态轮询不能创建部署任务，不能修改库存，不能让队列无限增长。
- 所有 ID、接口、Area、前缀和策略引用均进行服务端校验；不能通过 UI 或 API 注入 BIRD 语句。
- 保存后重启控制器、切换浏览器会话、使用第二个登录会话读取，配置和布局必须一致。
- MySQL revision 在并发读写下单调递增；任何失败写入不得产生半份 JSON 或半套远端配置。
- 记录关键变更、失败节点和回滚结果；普通状态检查不得刷屏式记录“候选配置检查通过”。

## 11. OSPF 状态机与跨层断言

一次变更的预期状态流转如下。测试时必须同时观察界面状态、HTTP 响应、控制器日志、库存 revision 和远端配置，不能只验证其中一个状态。

```text
草稿
  ├─ 本地校验失败 ───────────────> 草稿（字段错误，仍可编辑）
  ├─ 预检中 ── 失败 ──────────────> 草稿（无库存/远端变化）
  └─ 预检通过
       └─ 保存并应用中
            ├─ 节点失败 ──────────> 回滚中 ──> 已回滚/部分未知
            ├─ CAS 冲突 ───────────> 重新读取并重试（最多 3 次）
            └─ 全部节点成功 + CAS 成功 -> 已提交 -> 重新读取运行态
```

### 状态机用例

| ID | 场景 | 步骤 | 必须同时满足的断言 | 级别 |
| --- | --- | --- | --- | --- |
| OSPF-STATE-001 | 草稿本地错误 | 填写非法 Area、空接口或非法 Cost | 对应字段标红并可定位；不发出部署请求；草稿保留；其它控件可操作 | P0 |
| OSPF-STATE-002 | 预检进行中 | 在预检返回前切换节点、滚动画布、打开详情 | 页面仅显示预检区域遮罩；不抢焦点、不关闭键盘；不产生第二个预检 | P1 |
| OSPF-STATE-003 | 预检失败 | 注入 BIRD stderr 或节点超时 | 展示具体节点/字段和 stderr；库存 revision、远端活动配置、恢复日志均不变 | P0 |
| OSPF-STATE-004 | 应用进行中 | 注入 5 秒远端应用延迟并请求健康检查 | 顶部置顶等待框可见；健康检查和其它节点查询仍在有界超时内返回；不能重复应用 | P0 |
| OSPF-STATE-005 | 应用部分失败 | n1 成功、n2 失败 | n1 按逆序恢复；n2 无半成品；库存不提交；journal 有可恢复记录 | P0 |
| OSPF-STATE-006 | 应用后响应丢失 | 让 CAS 已提交但客户端连接断开，再重复相同请求 | 服务端状态只存在一个版本；重试幂等；不回滚已提交配置 | P0 |
| OSPF-STATE-007 | 控制器中断恢复 | 在应用或回滚阶段终止控制器后重启 | 启动恢复只执行一次；journal 被清理或标记最终状态；新请求可继续处理 | P0 |
| OSPF-STATE-008 | 完成后刷新 | 保存成功后不手动刷新页面 | 域、按钮、节点状态、邻居、路由和配置预览自动读取最新权威状态 | P1 |
| OSPF-STATE-009 | 单节点锁范围 | 让 n1 资源应用延迟，同时查询/编辑 n2 和控制器健康状态 | 仅 n1 显示等待或锁定；n2 和只读接口在有界时间内可操作；队列无无界增长 | P0 |
| OSPF-STATE-010 | 失效遮罩清理 | 预检、应用、详情、布局保存分别注入超时、4xx、5xx 和网络断开 | 所有遮罩、按钮禁用和 aria-busy 状态均恢复；草稿和错误字段保留，可再次提交 | P0 |

### 预检、预览与实际配置一致性

对每个支持的节点和地址族保存以下三份内容并逐项比较：

1. `POST /api/ospf/preview` 响应中的节点配置；
2. 保存并应用后远端 Include/generated 文件；
3. BIRD 当前活动配置（`birdc show status`、`show protocols all`，必要时导出配置片段）。

协议名、Router ID、Interface、Area、策略顺序和所有显式高级选项必须一致。允许出现格式化空白差异，不允许出现选项缺失、额外协议、错误节点或错误地址族。对每个节点使用 SHA256 和规范化文本 diff 留证。

## 14. 故障注入矩阵与预期恢复

故障注入必须在隔离环境执行。每项故障都要记录注入时机、受影响节点、恢复动作和最终状态，不能只记录 HTTP 错误字符串。

| 故障 | 注入方式 | 预期控制器行为 | 远端/库存检查 |
| --- | --- | --- | --- |
| 首节点预检失败 | `bird -p` 返回语法错误 | 不应用任何节点；返回字段和 stderr | 所有节点配置 SHA 与测试前相同，revision 不变 |
| 中间节点应用失败 | RPC 返回超时或 configure 失败 | 逆序回滚已应用节点，标记失败节点 | 无半份 Include；journal 可恢复或清理 |
| 回滚失败 | 让恢复 RPC 也失败 | 返回“部分未知”而非成功；保留恢复日志和节点列表 | 控制器仍可健康检查；禁止下一次覆盖未知状态 |
| Agent 断线 | 应用中断 TCP/停止 Agent | 目标节点有界超时；其它节点继续或按事务规则回滚 | 重连后可再次预检；不生成重复协议 |
| SSH 不可达 | 防火墙拒绝/Host unreachable | 单 SSH 节点失败可读；不阻塞 Agent 节点和 API | 已成功节点按规则回滚 |
| 数据库不可写 | CAS/commit 返回连接错误 | 远端先回滚，返回可重试错误 | 库存 revision 不前进，journal 不丢失 |
| 控制器被杀 | `SIGTERM`/进程崩溃 | 启动恢复按 journal 决定提交或回滚，且只执行一次 | 活动配置、库存和 journal 最终一致 |
| BIRD 配置被外部修改 | 应用前后修改用户主配置/Include | 检测到 Include 或版本不匹配时拒绝覆盖 | 原配置保留，向用户说明外部变更 |
| 大量无关轮询 | 高频 dashboard/runtime 请求 | 查询有界、只读、可降级；不占满部署队列 | revision 不变，部署任务数不增加 |

## 15. 执行记录模板与缺陷判定

每个用例复制以下模板填写，模板中的“通过”必须有证据链接或文件路径：

```markdown
## OSPF-XXX-000 <用例名称>

- 结果：通过 / 失败 / 阻塞 / 未执行
- 严重级别：P0 / P1 / P2 / P3
- 构建版本：
- 控制器、Node、浏览器、BIRD、Agent 版本：
- 测试节点/域/链路：
- 前置快照：artifacts/ospf/<run-id>/inventory-before.json
- 操作步骤：
  1.
  2.
- 预期结果：
- 实际结果：
- HTTP/BIRD/Agent 输出：
- 配置或状态 diff：
- 截图、trace、日志：
- 缺陷编号：无 / BUG-
- 清理结果：已恢复 / 未恢复（说明原因）
```

缺陷判定规则：

- 预览和实际下发不一致、错误节点配置被覆盖、库存与远端分裂、回滚失败未阻断后续操作、页面永久不可交互，均为 P0。
- 单节点详情错误、单个高级选项错误、移动端专属流程失败或单域不可用，通常为 P1；若能影响路由传播或批量部署则升级为 P0。
